# 0011 · 10-bit 软解路径（右对齐 16 位容器）

| 项 | 值 |
|---|---|
| 提交 | `feat(ffsw): 10-bit 软解路径（0011）` |
| 日期 | 2026-09-24 |
| 阶段 | P0 |
| 依赖 | 0010（`ffsw` 本体）、0006（色彩层已实现两种对齐的还原） |

## 这个功能点做了什么

`ffsw` 现在能解 10-bit 片源，并把结果按**本项目唯一的约定**交给上层：4:2:0
半平面、每样值 16 位容器、**右对齐**（10 位有效码值放在低位）。

帧上的表现是 `bit_depth = 10`、`y_stride = uv_stride = width * 2`。0010 里
"10-bit 显式失败并指向 0011"的那条路径已经换成真解码。

12-bit（`yuv420p12le` / P012）仍然显式失败——见实现要点第 3 条。

## 为什么现在做

0010 刻意把 10-bit 挡在门外：**宁可报错，也不静默降到 8-bit**——那会让 HDR/10-bit
片源悄悄丢掉低两位，动态范围被压掉而使用者看不出来。挡住的代价是这类片源完全
不能播，所以这一步必须紧跟着补上。

core 侧的准备其实早就做好了：0006 的色彩层把"右对齐"与"P010 左对齐"两种约定都
实现成了可验证的换算，缺的只是这条把数据搬过来的通路上的一段。

## 实现要点

### 1. 选型：为什么是 "P010 + 原地右移"，而不是某个右对齐格式

先把候选摆出来，都是实测的（160x120、25 帧、单帧字节数由 ffmpeg 的输出量出来）：

| 格式 | 布局 | 对齐 | 实测单帧 |
|---|---|---|---|
| `yuv420p10le` | 平面 4:2:0，三个平面 | 右对齐 | 57 600 B |
| `P010LE` | 半平面 4:2:0，16 位容器 | **MSB 对齐**（`1023 << 6`） | 57 600 B |
| `NV20LE` | 半平面 **4:2:2**（色度只水平下采样） | 右对齐（实测上界 1023） | 76 800 B |

三个都差一点：

- `yuv420p10le` 对齐对，但它是**平面**格式，而本项目的帧契约是"一张亮度平面 +
  一张交织 CbCr 平面"（`core/backend.zig` 的 `CpuPlanes` 只有 `y` / `uv`）。
- `P010` 布局对，但**对齐反了**（MSB 对齐）。
- `NV20` 对齐对、布局看起来也像，但它是 **4:2:2**：色度平面是整高。头文件里
  "色度半分辨率"的承诺会让消费者按 `(h+1)/2` 行去读，读到的就是错位的数据。
  这一条是我按 ffmpeg 头文件的注释（`interleaved chroma YUV 4:2:2`）加上单帧
  字节数（76 800 = 38 400 + 38 400）一起确认的，光看名字会以为它是 NV12 的
  16 位版本。

所以选**布局对的 P010 + 一次原地右移**。代价与收益写在下一节。

### 2. 一次额外遍历换来"一帧只有一种对齐约定"

右移是 `1.5 * w * h` 个样值的一次内存遍历（`right_align_in_place`）。它的收益
不是性能而是**契约的单一性**：帧结构里只有 `bit_depth`，没有"对齐方式"这一位，
所以如果 10-bit 帧可能是 P010 也可能是右对齐，每个消费者都得再问一次。

替代方案（把对齐方式加进帧结构、让 shader 分别处理）被否掉了：那等于把"哪来的
帧"这件事泄漏到呈现层，而 0006 已经把两种约定的换算做成同一套数学了。

### 3. 12-bit 仍然显式失败

`yuv420p12le` / `P012` 不在承诺范围内。这里同样不静默截断：把 12 位砍成 10 位
是丢掉一段动态范围，肉眼不一定看得出来。失败信息写的是"只支持 8-bit 与 10-bit"。

### 4. 内存：10-bit 的槽位是 8-bit 的两倍

槽位按"每样值字节数"统一算尺寸，所以 10-bit 下一块 1080p 槽位约 6 MB，12 槽的
上限是约 74 MB/路（实际按需分配，稳定态只占队列深度那几块）。这是 CPU 解码
通路的固有代价——帧在系统内存里，不像硬解那样有 GPU 常驻表面可以别名。

## 自检覆盖了什么

在 0010 那 30 项之上，10-bit 让结构检查从"写死 8-bit"变成按位深走：

| 检查 | 锁定的行为 |
|---|---|
| `首帧位深是 8 或 10` | 两条通路都在 |
| `亮度 stride == 宽度 x 每样值字节数（紧凑）` | 10-bit 是 `width * 2` |
| `色度 stride 同上（交织 CbCr 平面）` | 半平面布局在两条位深下同构 |
| `亮度最大码值在有效位深内` | **右对齐**：10-bit 上界 1023；若被当成 P010 左对齐会看到 65 472 这个量级——这条不依赖与 ffmpeg 的比对，是独立的结构断言 |

外加两个场景的逐字节比对（见下）。10-bit 的转储按平面（Y/Cb/Cr）写出，好和
ffmpeg 的 `-pix_fmt yuv420p10le` 对齐——由于 ffmpeg 没有"右对齐的 4:2:0 半平面"
格式，半平面那一侧没有可比的对照。拆交织只发生在转储里；帧本身仍是"亮度 +
交织 CbCr"，由上面的结构检查守着。

## 验证方式与结果

```bash
zig build test            # 114/114 通过（未受影响）
zig build ffsw-selftest   # 11/11 步成功；每个场景 31 项检查 0 失败
```

四组对照全部**逐字节一致**（`cmp` 在构建步骤里，不一致就会让这一步失败）：

| 片源 | 编码 / 像素格式 | 对照格式 | 帧数 | 字节数 |
|---|---|---|---|---|
| 320x240@25，2 秒 | mpeg4 / yuv420p | `nv12` | 50 | 5 760 000 |
| 160x120@25，1 秒 | H.264 High 4:4:4 | `nv12` | 25 | 720 000 |
| 160x120@25，1 秒 | H.264 High 10 / yuv420p10le | `yuv420p10le` | 25 | 1 440 000 |
| 160x120@25，1 秒 | FFV1 / yuv422p10le | `yuv420p10le` | 25 | 1 440 000 |

构建门禁里的两个场景是"8-bit 4:2:0"与"10-bit 4:2:0"（后者用 FFV1，因为它是
内置编码器，不依赖 libx264 的 10-bit 构建）；另外两组是我在开发时手工跑的同一套
比对，用来确认 4:4:4 的色度下采样与 4:2:2 的垂直下采样都不出偏差。

## 已知限制 / 下一步

- **12-bit 未做**，且不在承诺范围内。
- **端序固定小端**：`P010LE` 与 u16 的移位都按小端写。三个目标平台都是小端，
  将来若上大端需要在这里分叉（代码里有注释指路）。
- **10-bit 的手工对照只覆盖 H.264 High10 与 FFV1**；`P010` 直出的硬解路径
  （VAAPI / VideoToolbox 的 x420）属于 0017 / 0015，不在本步范围内。
- **HDR 的传输函数仍是 0023**：本步只解决"位深与对齐"，PQ / HLG 的色调映射
  还没做——所以 10-bit 片源现在能正确出帧，但 HDR 亮度尚未被正确映射到 SDR 输出。
- 内存占用随位深翻倍（见实现要点第 4 条）。
- 下一步（0012）：解码烟测工具 `zig build decode-smoke`，不需要 Godot、可以直接
  喂 URL，把"解码能不能跑"从本步的自检升级成可进 CI 的常规关卡。
