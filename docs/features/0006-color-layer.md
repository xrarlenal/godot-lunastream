| 项 | 值 |

| 日期 | 2026-09-24 |
| 阶段 | P0 |
| 依赖 | 无 |

## 这个功能点做了什么

core 现在能把"解码器给出的色域标签 + 原始码值"换算成归一化的 RGB：

- `Coefficients.bt601() / bt709() / bt2020()` —— 三条色域的 YCbCr 系数；
- `SampleLayout` —— 位深（8/10）与码值对齐方式（右对齐 / P010 左对齐）；
- `normalizeLuma` / `normalizeChroma` —— 视频范围与全范围的归一化；
- `ycbcrToRgb` —— 最终换算。

## 为什么现在做

色彩错了是**最难自证的一类 bug**：人眼没有绝对色标，看到偏色第一反应是"这素材
就这样吧"。而它偏偏又是纯数学，可以在没有 GPU 的机器上逐条验算。所以趁公式还没
被 shader 的调试噪声掩盖，先把它钉死。

## 实现要点

### 三件容易错的事，各自有测试

| 事项 | 弄错的表现 | 覆盖它的测试 |
|---|---|---|
| 色域矩阵（601 / 709 / 2020） | 肤色偏绿或偏品红 | 三条色域系数对照 ITU 参考值 |
| 码值范围（视频 / 全范围） | 整体发灰（对比度被压缩） | 白点 / 黑点在两种范围下的值 |
| 位深与对齐（右对齐 / P010） | 整体发暗（多移 6 位）或对比度减半 | 0..1023 逐码值双向验证 |

### 位深做成枚举，非法状态不可表达

源工程的位深是 `u8` 字段，于是每个 switch 都要写一条"不可能走到"的兜底分支。
这里改成 `BitDepth` 枚举（`eight` / `ten`），分支穷尽，兜底消失。

### 一处真实的错被测试抓到

最初把全范围的色度中性点写成 `maxCode / 2`，也就是 8-bit 的 127.5。两条测试立刻
红了。正确值是 `2^(位深-1)`（8-bit 的 128、10-bit 的 512）——差这半格会让纯灰
画面解出约 0.002 的偏色。于是加了 `midCode()` 把这个常数单独命名，并在注释里
写明它**不等于** `maxCode/2`。

这一条本身就是这个功能点值得单独提交的理由：如果公式先写进 shader，这半格的
偏差会在"颜色好像有点不对"里被吞掉。

### 10-bit 的两种约定逐码值验证

右对齐（FFmpeg 软解的 `yuv420p10le`）与左对齐（VAAPI 的 P010、CoreVideo 的
x420）必须还原出同一个有效码值。测试对 0..1023 全部扫一遍，同时验证两条路径的
归一化结果完全相同。另有一条测试记录"把对齐方式解释反"的量化后果：白点 940 会
被读成 14.6875，比视频范围的黑还低，画面掉进黑里。

## 刻意没有在本步做的三件事

| 没做的 | 为什么 | 什么时候做 |
|---|---|---|
| **GLSL 常数对照测试** | 源工程有一条测试解析 shader 源码文本、逐个比对 Zig 与 GLSL 的常数，防止两边各自漂移。它要求 shader 文件存在，而现在还没有 | 写 shader 的那一步（呈现层） |
| **推送常量（push constant）的 ABI** | 它是 CPU 与 GPU 之间的结构体布局，必须和它的消费者一起定；先冻结一个没有消费者的 ABI 属于投机 | 同上 |
| **HDR 传输函数（PQ / HLG / 色调映射 / BT.2020→BT.709）** | 只在**可选的** HDR 输出模式下才会走到，默认 SDR 路径用不到；且它与 GLSL 共享常数，和上面两项是同一批工作 | 见推进表新增的独立条目 |

第三项要特别说明：推进表原本把"HDR"写在 0006 这一行里。这次**显式拆出来**，
而不是悄悄不做——它在表里有了自己的编号。

## 单元测试覆盖了什么

| 测试 | 锁定的行为 |
|---|---|
| `BT.601 / BT.709 / BT.2020 系数与 ITU-R 一致` | 三条色域的 Kr/Kb/派生增益 |
| `Kg 恒等于 1-Kr-Kb（三条色域的构造约束）` | 系数不是手写而是推导出来的 |
| `未指定色域时返回 null 而不是猜一个` | 标签缺失时由调用方决策 |
| `8-bit 视频范围白点 (235,128,128) 解码为纯白` | 白点不偏色 |
| `8-bit 视频范围黑点 (16,128,128) 解码为纯黑` | 黑点不抬灰 |
| `8-bit 全范围白点与黑点` | 全范围基准 |
| `视频范围与全范围对同一个 Y 值给出不同亮度` | 两种范围确实不同（这就是发灰的来源） |
| `色度中性点在两种范围下都解码为 0` | 中性灰不偏色（含 8/10 位深） |
| `10-bit 视频范围白点与黑点` | 10-bit 基准 64 / 940 |
| `10-bit 右对齐与左对齐（P010）逐码值还原一致` | 0..1023 全扫，两种约定等价 |
| `10-bit 左对齐在容器里的最大值正好是 16-bit 上界附近` | P010 填充方式（1023<<6 = 65472） |
| `BT.2020 与 BT.709 对同一 YCbCr 给出不同 RGB` | UHD 与 HD 确实不同，不能混用 |
| `红色主导的 YCbCr 解出 R 分量为最大` | 换算方向没反 |
| `把对齐方式解释反了会整体发暗（记录失效模式）` | 失效模式有量化对照 |

## 验证方式与结果

```bash
zig build test
```

结果：**65/65 通过**（其中本功能点新增 16 个）。

## 已知限制 / 下一步

- 归一化结果**不夹取**：Y 超出 [16,235] 会得到负值或大于 1 的值。超黑/超白在
  广播素材里是合法信息，夹取留给输出端（纹理格式本身就会饱和）。
- 只支持 8 / 10 位深。12-bit 在类型层面就无法表达。
- 色彩原色（BT.709 / BT.2020 primaries）与传输函数标签本步未建模型——只有需要
  HDR 或广色域时才用得上，和上面拆出去的 HDR 条目一起做。
- 下一步（0007）：线程原语与有界 worker 池。它是解码调度的载体，也是 core 里
  唯一需要真并发的一层。
