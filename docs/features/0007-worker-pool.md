## 这个功能点做了什么

core 里唯一需要真并发的一层写完了，由三块组成：

| 模块 | 职责 |
|---|---|
| `sys_clock.zig` | 线程原语与单调时钟：把 Zig 0.16 的 `std.Io` 收成无参门面（`Mutex` / `Condition` / `sleep` / 单调时间戳） |
| `backend.zig` | 解码后端接口：ptr + vtable，调度器不需要知道背后是 VideoToolbox、D3D11VA、VAAPI 还是软解 |
| `decode_scheduler.zig` | 有界共享 worker 池：固定线程数、每路流串行解码、注册/注销与在途工作排序 |

## 为什么现在做

并发契约是**用肉眼最不可能验证**的一类东西——"每路流没有被两个线程同时解码"这种
性质，在真机上跑一天也未必暴露一次。而它一旦破了，表现是随机花屏或偶发崩溃。

解法是先把后端做成可替换的 vtable：测试用假后端就能在任何机器上验证调度逻辑，
不需要 GPU、不需要摄像头。测试里有一条专门断言"假后端观测到的最大并发恒为 1"。

## 实现要点

### Zig 0.16 的 `std.Io` 适配为什么是安全的

0.16 把 `std.Thread.Mutex` / `Condition` / `sleep` / `std.time.*` 都挪到了
`std.Io` 之下，每个调用都要一个 `Io` 实例。本项目的线程全部由 `std.Thread.spawn`
直接创建，没有事件循环、没有取消语义，所以用 `Io.Threaded.global_single_threaded`
作后端：它只关掉 `Io` 自己的异步任务调度，futex 操作仍然是真正的系统 futex，
跨自建 worker 线程完全正确。

### 线程契约（这一层的承重墙）

- **worker 数量固定**，与流的数量无关——加流不加线程，有一条测试断言注册第二路流
  前后 `workerCount()` 不变。
- **每路流串行解码**：靠 `queued` / `busy` 这一对守卫，一条流永远不会同时交给两个
  worker。由此 `FrameQueue` 的 SPSC 契约成立（生产者始终只有一个），每路流的帧顺序
  也是确定的。
- **注销阻塞到在途的一轮结束**：`unregisterStream` 置 `dead` 后等 `busy` 落下，再
  释放缓冲帧、关后端、释放流。返回后句柄立即失效——不存在"边解码边销毁"。
- **worker 不碰任何 Godot / RenderingDevice API**。呈现与 GPU pass 始终在主线程。

### 表面数量公式把 0004 和这一层连起来

`requiredPoolDepth(queue_usable_depth, frame_latency) = 队列 + 1 + 回收环`。

这三项分别对应"同一时刻可能存活的三种表面"：排队等呈现的、正在转换/呈现的、
还被回收环扣着的。解码池按这个数开表面，后端就永远不会回收一块还在被读的表面。
它是 0004 那个 use-after-free 防护在"够不够用"这一侧的配对。

### 热路径免锁

`dead` 是只写一次的原子标志（而不是互斥锁保护的字段）：解码的内循环每帧都要读它，
用 acquire 读可以避免每帧抢一次锁。就绪表的出队用游标推进（摊还 O(1)），只有冷路径
（注销/租约接管）才真正移除元素。

### 单调性守卫与 0005 的接口

0005 里钉住了一条契约：呈现选择器**假设**帧按 PTS 非递减入队，遇到乱序会让播放
位置倒退。这一层就是发现违反的地方——`checkEnqueueMonotonic` 在首次发现回退时打一条
一次性告警（每条流只报一次），然后更新基线。它是纯诊断：从不重排、从不丢帧。

### 刻意收窄成 video-only

源工程的后端接口还带音频（`audio_track_*` / `next_audio_chunk`）与 seek。本插件的
后端只解视频，直播流也没有 seek 语义，所以这两组方法没有进来。若将来迁入带音频的
本地文件路径，它们会作为独立功能点补上。

### 强制同步调试模式

`force_synchronous` 置位时不创建任何 worker，解码在调用线程上同步跑完——这样
"解码→转换→呈现"的生命周期 bug 可以在没有任何线程交接的确定性条件下复现。该模式
只在 Debug / ReleaseSafe 下编译进来，ReleaseFast 里被强制为 false，避免发布版误走
同步路径；有一条测试断言它在阈值处生效（同步模式下 `workerCount() == 0`，但取帧
照常，且并发仍然为 1）。

## 单元测试覆盖了什么

| 测试 | 锁定的行为 |
|---|---|
| `互斥锁保护共享计数（两个线程各加 N 次）` | 锁真的互斥（1 万次无丢失） |
| `条件变量能唤醒等待方` | wait/signal 配对 |
| `sleep 真的等待` / `单调时钟不回退` | 时间原语的基本性质 |
| `色域默认值 / 协商默认值`（0006 遗留） | 标签的默认约定 |
| `VideoFrame.release 调用释放闭包，空闭包安全` | 帧释放语义 |
| `假后端可以通过 vtable 走完整条调用链` | 接口形状可用 |
| `requiredPoolDepth = 队列 + 1 + 回收环` | 表面数量公式 |
| `worker 数量被钳到至少 1，并如实上报` | 参数退化 |
| `注册后能按顺序取到帧（PTS 单调递增）` | 基本出帧 |
| `每路流串行解码：假后端观测到的最大并发恒为 1` | **承重墙** |
| `取走一帧会触发补货，直到后端的帧被取完` | 跨容量边界的补货 |
| `后端报 EOS 之后进入 atEnd，且不再请求新帧` | EOS 语义 |
| `多路流共享同一个池：加流不加线程` | 有界性 |
| `注销会释放队列里所有缓冲帧并关闭后端` | 无泄漏、无 use-after-free |
| `deinit 会清理没有注销的流` | 析构兜底 |
| `同步调试模式不创建线程，但仍然遵守契约并能出帧` | 调试模式等价性 |
| `peek …` ×2 | 前瞻接口不消费队列 |
| `入队单调性守卫：PTS 回退时置位一次性告警闩锁` | 与 0005 的契约对接 |

zig build test

结果：**86/86 通过**（其中本功能点新增 21 个：线程原语 4 + 后端接口 4 + 调度器 13）。

## 已知限制 / 下一步

- **没有 seek**：直播流不需要；若要支持本地文件回放，需要在后端接口与调度器
  两侧同时补（源工程对应的是 `requestSeek` / `seekExact` 与 scrubbing 路径）。
- **worker 数量目前是常量 3**：源工程提过按 CPU 核数调整，但实测显示软解单帧
  耗时远小于一帧预算，暂时不必。改之前先有测量。
- **表面数量公式还没有消费者**：它现在是纯函数，真正"按它去开表面池"要等平台
  后端接入（呈现层）。
- 只在 macOS 上跑过；线程原语与调度器本身是平台无关的，但 Windows / Linux 的
  CI 还没有。
- 下一步（0008）：播放控制器与状态机。它把时钟、队列、选择器、回收环四样东西
  串成"一路流的一帧生命周期"，并对外给出可上报的状态。
