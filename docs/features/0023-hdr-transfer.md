## 这个功能点做了什么

10-bit 片源**能解出来**（0011）之后，还差"它的亮度怎么落到 SDR 显示上"。这一层补上
三件事，全部在 core：

| 输入 | 处理 |
|---|---|
| PQ（SMPTE ST 2084，HDR10） | 电信号 → 相对亮度（0..1，1 = 10000 nits），并给出逆函数 |
| HLG（BT.2100） | 电信号 → 场景线性光（含逆函数） |
| BT.2020 原色 | 线性矩阵换算到 BT.709（负值钳位） |
| 任意 HDR 亮度 | 扩展 Reinhard 色调映射到 SDR 的 [0,1] |

## 为什么放在 core 而不是着色器

这些是**有标准答案的数学**：曲线有端点、有单调性、有可逆性，矩阵有行和。放在 core
就能逐条对照标准值写测试；一旦搬进 GLSL，就只能靠肉眼看画面——而"亮度映射不对"
恰恰是最难看出来的一类问题（人眼对绝对亮度没有标尺）。

着色器那边将来只接受这里算出来的常数（推送常量），与 0006 的分工一致。

## 实现要点与可验证的性质

### 1. 常数按标准写成有理数

PQ 的 `m1 = 2610/16384`、`m2 = 2523/4096*128`、`c1 = 3424/4096`、`c2 = 2413/4096*32`、
`c3 = 2392/4096*32` 全部照标准写成除法，而不是手抄小数——手抄少一位，曲线就有个
看不出来的偏差。

### 2. 曲线用"可逆"当自检

`pq.fromRelativeLuminance(pq.toRelativeLuminance(e)) == e` 在 0..1 上逐点比对
（误差 1e-9），HLG 同理。可逆性是"曲线抄没抄错"最直接的证据：任何一处常数错了，
逆函数就对不上。

### 3. 矩阵用"行和为 1"当自检

BT.2020 → BT.709 的矩阵，三行和都必须是 1（白点不变）。抄错任何一个系数，纯白就会
变成偏色——而那正是最难肉眼发现的一类错。另有一条测试记录"BT.2020 的纯绿在 BT.709
里会越界（负值被钳掉）"，说明色域收窄的固有代价。

### 4. 色调映射曲线的三条定义性性质

扩展 Reinhard：`out = x(1 + x/w²)/(1 + x)`，其中 `x = nits/peak`、`w = white/peak`。

| 性质 | 含义 | 测试 |
|---|---|---|
| `x = w` → 1 | 白点映射到 SDR 白 | ✅ |
| `w = 1`（峰值即白点）→ 恒等 | 不动 SDR 素材 | ✅ |
| 峰值以上钳在 1、且单调不减 | 高光不溢出 | ✅ |

另有一条记录"白点低于峰值时中低亮度被抬高"（500 nits 在峰值 4000 的素材里明显亮于
按峰值线性的 0.125）——这就是 HDR 色调映射不该"整体压暗"的原因。

## 我自己算错的两处（留档）

1. **PQ 在 10% 电信号处是约 0.32 nits，不是 6 nits**。我第一版按"0.0006 相对亮度"
   写了期望，测试红了才算清楚——差了一个数量级。现在把"约 0.32 nits"写进测试注释。
2. **色调映射的归一化基准我写反了两次**：先是按白点归一（导致峰值不收敛），改成按
   峰值归一后又把"中点被抬高"写成"中点被压暗"。两次都是测试红了才发现的——那三条
   定义性性质就是为了让这类错误无处可藏才写的。

## 已知限制 / 下一步

- **不做 OOTF**（HLG 的系统伽马）：它取决于显示端峰值亮度与观看环境，属于显示端策略。
- **不做感知色域映射**：BT.2020 → BT.709 只做线性矩阵 + 钳位；CAM16 那一类需要显示端
  信息，不是解码端的职责。
- **还没接进着色器**：`output_mode`（SDR/HDR）属性与把这里的常数送进 compute 的接线
  属于呈现管线那一步；本步只把"有标准答案的数学"落到 core 并验证。
- 峰值/白点是参数（`ToneMap`），默认 1000/1000（即恒等）；真机联调时按素材定。
