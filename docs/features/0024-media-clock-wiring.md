# 0024 · 接上 MediaClock 与重连后的 reanchor

| 项 | 值 |
|---|---|
| 提交 | `feat(godot): 接上 MediaClock，重连后位置不倒退（0024）` |
| 日期 | 2026-09-25 |
| 阶段 | P0 |
| 依赖 | 0001（MediaClock 本体）、0019（重连） |

## 这个功能点做了什么

播放位置不再取"最近一帧的 PTS"，而是由 core 的 `MediaClock`（0001）供给：

- 每帧 `advance(delta)` 按渲染节奏推进；
- 每收到一帧 `reanchor(pts)` 向前对齐（**只向前**）；
- `_getPlaybackPosition()` 返回 `clock.mediaTime()`；
- 暂停时 `setPaused` 同步到时钟。

## 为什么必须做（0019 暴露出来的）

重连会让源从头开始给 PTS。实测在调度器里能看到 core 的单调性守卫告警：

```
视频 PTS 在入队边界回退：0.0000s 出现在 0.0667s 之后且没有 seek
```

如果播放位置直接取帧的 PTS，那么"断流重连"在用户看来就是**画面时间跳回开头**——
面板上的进度条会莫名其妙地归零。0001 当初就是为这件事写的 `reanchor`（只向前、
且返回是否生效），但那时没有播放链路可接；这一步把它接上。

## 实现要点

1. **时钟与 PTS 的分工**：时钟负责"这一刻应该播到哪"，PTS 负责"这一帧是什么时刻"。
   两者只在 `reanchor` 处相遇，而 `reanchor` 只向前——所以源的时间戳重置不会让播放
   位置倒退，画面也不会卡住（时钟仍在按 delta 前进，直到新帧到来再对齐）。
2. **多取一个返回值**：`reanchor` 返回 bool（是否真的锚定了）。这里用 `_ =` 丢掉，
   但那个返回值对调试有价值（能区分"锚定生效"与"锚定被忽略"两种现场，0001 的文档
   里写过这个设计意图）。
3. **`_seek` 仍然是空操作**：seek 是"源的语义"，而本插件的源（直播流 / 本地文件）
   都不支持；只挪时钟会让画面与位置脱节。这一条与插件定位一致，写在播放实现的注释里。

## 验证

**core 单测**（同步、确定性地复现重连场景）：

```
重连场景：源的 PTS 从头开始，播放位置不倒退（0024）
```

它模拟"播到 5 秒 → 重连后 PTS 从 0.0/0.04 来"，断言 `reanchor` 两次都返回 false
（回拨被忽略）、位置不倒退、而时钟继续前进。core 因此 155/155。

**引擎内**（`zig build godot-playback-smoke`）新增一条：逐帧采样
`VideoStreamPlayer.stream_position`，断言单调不减。

```
PASS  播放位置在推进  0.36
PASS  播放位置逐帧单调不减  last=0.360
RESULT=PASS
```

## 已知限制 / 下一步

- 这条断言在**真的发生重连**时才最有力。现在的烟测里源从头到尾是健康的，所以它验证
  的是"时钟在正常播放时单调"；重连路径由 core 那条场景测试覆盖（确定性地构造了 PTS
  重置）。要端到端复现，得让源在播放中途死掉——可以借 0010 那套 UDP 推流"推几秒就停"
  的做法做一个引擎内用例。
- 音画同步不在范围内（本插件只做视频，0001 的文档写明了这一点）。
