# 0012 · 解码烟测工具（`zig build decode-smoke`）

| 项 | 值 |
|---|---|
| 提交 | `feat(ffsw): decode-smoke 解码烟测工具（0012）` |
| 日期 | 2026-09-24 |
| 阶段 | P0 |
| 依赖 | 0010（解封装 + 软解）、0011（10-bit） |

## 这个功能点做了什么

仓库有了一个不需要 Godot 的入口来回答"这条源能不能解、解得快不快"：

```bash
zig build decode-smoke                                   # 默认跑生成的 960x540 片源
<构建产物 decode_smoke> rtsp://192.168.1.64:8554/stream --frames 300
<构建产物 decode_smoke> clip.mp4 --timeout-us 2000000
```

它把"解码能不能跑"与"Godot 里能不能出画"彻底分开——前者现在既可以在任何机器上
一条命令跑完，也可以在真实摄像头上跑（这是它存在的最大价值：**排查现场问题时，
不必先把 Godot 拉起来**）。

## 为什么现在做

0010 / 0011 已经有了断言"解得对不对"的自检，但那个自检是**构建门禁**：它跑的是
生成的片源、比的是字节、判据是结构与内容。现场需要的是另一件事——把任意一条源
喂进去，看它协商到什么色域、解出多少帧、每帧多久、有没有坏包、结束得干不干净。

目标写在 PLAN 的能力基线里（"无 Godot 的解码烟测 `zig build decode-smoke` /
`decode-smoke-sw`，可直接喂 URL"），有了它，CI 才有一条"解码这一层没坏"的常规
关卡，而不是只靠 release 时手工验。

## 实现要点

### 1. 只有一条硬判据，其余都是观测

| 是判据 | 是观测 |
|---|---|
| 一帧都没解出来 → 退出码非 0 | 打开耗时、每帧毫秒、净载荷与折算带宽、丢弃坏包数、PTS 区间与单调性、结束方式 |

**计时不做断言**是刻意的：机器负载、电源策略、并发都会让它抖动，把抖动写进判据
只会制造假红灯，最后的结果通常是"把阈值放宽到没有意义"。性能要看数字，但不该
让构建去守那个数字。

### 2. 编码分类从**已打开的句柄**上取，不再 probe

第一版用 `nv_ffsw_probe` 打印编码分类——它是 0010 第 2 步为 `auto` 档写的轻量探测，
但**它会自己开一次源**。对文件无所谓；对摄像头等于多占一路连接，而有些设备会直接
拒绝第二路。于是把分类在 `open` 时记进句柄，新增
`nv_ffsw_open_codec_class(handle)`。判据是可观测的：mediamtx 的服务端日志里，
同一路源在改之前看到 2 个读取会话，改之后是 1 个。

`probe` 本身留着——`auto` 档的决策发生在"还没有句柄"的时候（0009 的语义就是
先分类再决定开不开硬解），那个场合它是对的。

### 3. 默认片源用内置编码器

默认场景的 960x540 片源用 `mpeg4` 编码（FFmpeg 内置），不依赖 `libx264`——否则
这一步在只装了 LGPL 构建的机器上就跑不起来。想看 H.264 基线，自己生成一段喂给
同一个二进制即可（下面就有这样一次手测）。

## 验证方式与结果

```bash
zig build decode-smoke    # 5/5 步成功，SMOKE=PASS
zig build ffsw-selftest   # 31 项检查 0 失败（未受影响）
zig build test            # 114/114（未受影响）
```

实测数字（macOS 26.5 / Apple Silicon，仅作量级参考）：

| 场景 | 帧数 | 每帧 |
|---|---|---|
| 960x540 mpeg4（构建门禁场景） | 60 | **0.19 ms** |
| 960x540 H.264（手工生成，`-O2`，`thread_count=1`） | 60 | **1.10 ms** |
| 320x240 H.264 over **RTSP**（mediamtx，实时） | 25 | **0.54 ms** |
| 160x120 H.264 High 10（10-bit） | 25 | 0.06 ms |

RTSP 那一路同时确认了承载：服务端日志写着
`is reading from path 'smoke5', with TCP, 1 track (H264)`——**1 路会话**（改之前
是 2 路），承载是 TCP。

### 与源工程基线的偏差（如实记录）

PLAN 里记着源工程的基线是"软解 H.264 960×540 单帧 0.49 ms"。这里手测同一分辨率
是 **1.10 ms**，约 2.2 倍。两条候选解释，我**没有**做进一步定位，所以不下结论：

1. `-O0` 与 `-O2` 几乎没有差别（1.128 → 1.104 ms），说明时间花在 libavcodec /
   libswscale 内部（预编译的优化库），不在我们这层包装上；
2. 这个 shim 刻意用 `thread_count = 1`（多路并行交给 core 的 worker 池），而源工程
   在单路测试时可能开着解码器内部帧线程；另外片源内容（`testsrc` 高频细节、
   码率偏高）会影响解码耗时。

要下结论需要"同一段片源 + 同一套线程设置"的对照实验。**但从余量上看这件事不紧急**：
1.10 ms/帧约等于 900 fps 的解码能力，而目标是 25/30 fps 的实时流。真要优化，第一
个旋钮是解码线程数，第二个是这一步额外做的 NV12 重排（0011 里 10-bit 还会多一次
右移遍历）。这里只把数字和不确定性一起留下。

## 已知限制 / 下一步

- **目前只有一个工具，没有 `decode-smoke` / `decode-smoke-sw` 这一对**：现在仓库里
  只有软解后端（`ffsw`），两个名字会是同一件事。等 0015–0017 的硬解后端落地，
  这一层才需要拆成"默认（可硬解）+ 强制软解"两种，与 0009 的档位语义对齐。
- 不参与 Godot：`ffsw` 仍未接进扩展（0018），所以这个工具的定位就是"引擎之外的
  那条腿"。
- 只在 macOS 上跑过。
- 下一步（0013）：CPU 帧导入器与轮换纹理池——把解码出来的 CPU NV12 变成
  `RenderingDevice` 纹理，这是呈现层的第一站。
