# 0005 · 呈现选择器（早到就等 / 迟到就丢）

| 项 | 值 |
|---|---|
| 提交 | `feat(core): 呈现选择器（早到就等 / 迟到就丢）` |
| 日期 | 2026-09-24 |
| 阶段 | P0 |
| 依赖 | 0001（主时钟提供 `now`） |

## 这个功能点做了什么

core 现在能回答"屏幕上该是哪一帧"：`selectPresentAction(head_pts, next_pts, now,
frame_interval)` 返回三个动作之一——`hold` / `drop` / `show`。解码线程提前解出
若干帧排好队，每个渲染 tick 由这个纯函数决定队首的去留。

## 为什么现在做

它是"跟不跟得上实时"的唯一判定点，也是弱网下体验好坏的分水岭。做成纯函数之后
可以被逐条穷举验证——而这正是那种"在真机上靠肉眼调、永远调不明白"的逻辑。

## 实现要点

### 三个动作，两条被刻意保护的边界

| 动作 | 条件 | 含义 |
|---|---|---|
| `hold` | 队首 PTS 还在未来 | 保持当前画面，本帧不上屏新内容 |
| `show` | 队首到期，且后继还没到期 | 队首就是此刻最新的一帧 |
| `drop` | 队首到期，且后继**也已到期** | 队首陈旧，丢掉它去追实时 |

**绝不空屏**：只剩一个到期帧时，即使它已迟到接近一个帧间隔，也仍然 `show`。
一帧在上屏期间本来就横跨约一个帧间隔，落后一点点是正常的；只有存在"更新且同样
到期"的帧可以替代它时才丢。这条边界若搞错，表现是画面周期性闪黑。

**绝不永久落后**：一旦积压，连续 `drop` 会在**同一个 tick 内**把积压收敛到只剩
一帧。这就是弱网下"回放变慢动作"的解药——丢掉旧的、直接跳到实时。有一条测试
专门模拟 4 帧积压并断言恰好 3 次 drop 后落定。

### 半个帧间隔的容差（eps）

PTS 会因为取整或时钟粒度落在 `now` 之后一丁点。不给容差的话，这一帧会被白白多等
一个 tick，表现为稳定的"每次都晚一帧"。所以 `head > now + eps` 才算未到，
`eps = frame_interval * 0.5`。`frame_interval` 传 0 或负数时退到极小兜底值，
避免把"正好到期"判成未到。

### 一条"上游契约"被钉进测试

这个函数只比较"每个 PTS 与 `now`"，**从不比较队首与后继的大小**。所以如果队列里
后继的 PTS 反而比队首小（B 帧，或后端泄漏了解码顺序），它会先丢掉较新的队首、
再显示较旧的后继——播放位置凭空后退一格。

这不是选择器能修的问题，而是队列**不允许**出现这种输入。所以把它写成一条测试：
给定乱序输入，选择器就会这样误判——让后来的人一眼看到这个函数的适用前提。
上游的保证落在解码后端必须按 PTS 单调入队（那一步会有对应的测试）。

## 刻意没有复刻的部分：SinkLatencyEstimator

源工程 `core/sink_latency.zig` 有一个"音频接收端抢跑深度估计器"，解决的是：
Godot 的音频混音接收端会先吞掉一大口（按 `buffering_msec`，约 0.68 秒）来预热
重采样环，而以"被接收的采样数"为准的主时钟会因此比实际听到的快一段，视频就会
领先音频。

**本插件不复刻它**，理由是本插件不碰音频：网络流后端（ffvt / ffd3d / ffva /
ffsw）只解视频，主时钟是单调推进的（0001），不存在"被音频接收端拉快"的问题，
该补偿量在本插件里恒为 0。源工程自己的注释也写了"静音片源的补偿恒为零"。

保留位置：若将来把带音频的本地文件路径（源工程的 avf / mf 后端）迁进来，
它必须作为**独立的一次功能点**回来，而不是现在预埋。

## 单元测试覆盖了什么

| 测试 | 锁定的行为 |
|---|---|
| `队列为空时保持当前画面` | 空队列不得空屏 |
| `队首在未来时保持当前画面（早到就等）` | hold-early |
| `正好到期的唯一一帧上屏` | 边界相等 |
| `轻微迟到但唯一的到期帧仍然上屏（绝不空屏）` | 迟到 0.6 帧仍 show |
| `队首陈旧且后继也已到期时丢掉队首（迟到就丢）` | drop-late |
| `队首到期而后继还在未来时显示队首` | 正常节奏下的判定 |
| `落在半个帧间隔容差内算到期` | eps 容忍取整误差 |
| `帧间隔传 0 或负数时仍能判定（兜底容差）` | 参数退化时不误判 |
| `乱序队列会让判定倒退（钉住上游的单调序契约）` | 适用前提被写成测试 |
| `连续 drop 在一个 tick 内把积压收敛到一帧` | 积压不变成慢动作 |
| `积压消化完之后队列空一帧时保持画面而非丢帧` | 收敛后不空屏 |

zig build test

结果：**49/49 通过**（其中本功能点新增 11 个）。

过程中撞到 Zig 的一条限制：错误值的名字必须是 ASCII 标识符，中文错误名会报

## 已知限制 / 下一步

- `frame_interval` 目前由调用方传入（`1/fps`）。**fps 从哪来**是解码那一步的
  问题：容器元数据里的帧率、或由相邻 PTS 差值估计——要到那时才有答案。
- 本函数不做"多久算真的卡住"的判断，那是播放控制器（0008）的状态机职责。
- 下一步（0006）：色彩矩阵与位深归一化——把 YCbCr 色域、HDR 传输函数与
  8/10-bit 归一化这些**纯数学**先锁死，因为它们错了表现为"画面颜色不对"，
  比闪烁更难定位。
