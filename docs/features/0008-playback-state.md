## 这个功能点做了什么

`src/core/playback_state.zig`：一路流的六态状态机 `idle / opening / playing /
stalled / failed / off`，加上指数退避的重连策略（首次 1.5 秒、每次翻倍、
封顶 8 秒、最多 8 次）。全部纯逻辑，能在没有网络、没有时钟、没有摄像头的机器上
把整条时间线跑一遍验证。

## 为什么范围是"状态机"而不是整个 playback_controller

源工程的 `playback_controller` 除状态机外还管音频混音与拖动 scrubbing。这两块在
本插件里已经分别在 0005（音频接收端抢跑补偿）与 0007（后端接口去掉 seek）的说明
里去掉了，理由都是同一个：本插件只解视频、直播流没有 seek 语义。

去掉之后剩下的、且真正需要在 core 里有唯一权威答案的，就是"现在是什么状态、
下一步该做什么"——也就是原 LunaFusion 里散在 GDScript 中那约 150 行样板的核心。
这是 0008 收敛成状态机的理由，不是漏做。

## 实现要点

### 两个终态，且只有一种方式离开

`failed`（重连次数用尽）与 `off`（显式停止）都是终态：`tick()` 在终态下永远返回
false，不产生重连请求。要重新开始只能由外部显式 `beginOpen()`。这一条有测试锁定，
因为它决定了"面板显示失败之后会不会自己偷偷重连"这种用户能看见的行为。

### 停滞判定优先于重连

`tick()` 先把状态如实降级为 `stalled`（让界面能立刻反映"没帧了"），再按退避窗口
决定要不要真的发起重连。如果反过来的话，界面上会跳过"停滞"直接显示"连接中"，
丢失了"其实是流断了"这个信息。

### 一条测试抓到的实现漏洞

写"停滞中的帧到达会立刻恢复 playing"时红了。原因是 `onFrame` 只处理了 `stalled`
分支，而 `tick()` 在请求重连时已经把状态推进到 `opening`——于是**重连成功、帧已经
到了，状态却一直卡在"连接中"**。改成对 `stalled` 与 `opening` 一视同仁地回到
`playing` 并清零重连计数。

留到真机上的表现是"画面已经恢复但面板一直显示连接中"——足以让人怀疑整个状态机。

## 单元测试覆盖了什么

| 测试 | 锁定的行为 |
|---|---|
| `初始状态是 idle，且不产生重连请求` | 初始态 |
| `发起连接后进入 opening` | 显式发起 |
| `首帧到达进入 playing 并把尝试次数清零` | 成功路径与计数重置 |
| `持续有帧就一直 playing` | 稳定态不会自己抖动 |
| `超过停滞阈值后降级为 stalled 并请求重连` | 阈值边界 + 降级顺序 |
| `重连间隔指数退避并封顶` | 3s→6s→8s→8s 序列 |
| `尝试次数用尽后进入 failed，且不再重连` | 终态语义 |
| `重连成功后回到 playing 并重置退避` | 恢复路径 |
| `停滞中的帧到达会立刻恢复 playing` | 上面那个漏洞 |
| `显式停止进入 off 终态` | 停止语义 |
| `failed 是终态：只有外部重新 beginOpen 才能再开始` | 终态可由外部解除 |

## 已知限制 / 下一步

- 阈值与退避参数目前是默认值（停滞 2 秒、退避 1.5→8 秒、8 次）。真机联调时
  按实际弱网表现再调，但调整只影响 `Policy`，不动状态机。
- 本模块不含"多久算连接超时"的独立超时——`opening` 状态下没有帧同样走停滞判定，
  这是刻意的简化：连接超时与中途掉线在用户看来是同一件事。
- 下一步（0009）：后端选择器与硬解名额预算。做完它，core 层封顶。
