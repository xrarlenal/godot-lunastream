## 这个功能点做了什么

每路流的解码器策略（`auto` / `hardware` / `software`）与一个**全局**的硬解会话
名额预算。做完它，core 层封顶。

## 为什么需要"名额"而不是看 GPU 利用率

真正稀缺的资源不是 GPU 算力，而是**并发解码会话数**——它才是会真失败的那个，
也是运维能理解和能调的旋钮。采样 GPU 负载既做不到跨平台可移植，采样窗口本身
还会引入抖动。

## 三条语义（差别不是措辞）

| 档位 | 行为 |
|---|---|
| `hardware` | 只用硬解，失败就是失败，**绝不悄悄落软解**；名额满也照样占（显式指令优先，计数保持诚实） |
| `software` | 只用软解，不碰名额 |
| `auto` | 编码不在平台白名单 → 软解（**格式兜底**）；在白名单但名额满 → 软解并标记 `hardware_saturated` |

`auto` 走软解时会把"格式不支持"和"名额溢出"在上报里区分开——这两种情况在用户
看来都是"没走硬解"，但原因完全不同，混在一起就没法排查。

而 `hardware` 档的关键承诺是：**用户永远不会拿到一个"看起来是硬解其实是软解"的
假象**。这一条由测试 `hardware 档即使格式不在白名单也不降级` 锁定。

## 刻意不做自动回切

因名额满而走了软解的 `auto` 通道，即使之后名额空出来也不自己切回硬解，要等下次
open/重连重新评估。自动回切会让两路流在名额临界点附近来回抖动，代价远大于收益。

## 白名单是编译期常量，不是能力探测

`hardwareWhitelist` 里每一条都对应一个真写过的后端实现：macOS 的 `ffvt` 只做了
H.264（HEVC 走软解），Windows 的 `ffd3d` 与 Linux 的 `ffva` 覆盖 H.264/HEVC。
把它写成常量表而不是运行期探测，是因为"这个平台的后端实现了没有"是代码事实，
探测只会引入不确定性。

## 容易漏的一处：名额的释放时机

拿到硬解时名额已经占用，必须在**三个地方**释放：重新 open 前、open 中途失败时、
销毁时。漏一处就会永久饿死后续通道——所以 `release()` 用了饱和减法
（`-|=`），重复释放不会回绕成一个巨大的数，把整个预算废掉。

## 单元测试覆盖了什么

| 测试 | 锁定的行为 |
|---|---|
| `越界的档位值返回 null（调用方保持原值）` | 脚本传错值不污染状态 |
| `硬解白名单与三个后端的实现一致` | macOS 无 HEVC、Windows/Linux 有 |
| `auto：编码不在白名单时走软解，且不算名额溢出` | 格式兜底 ≠ 溢出 |
| `auto：白名单内且有名额时走硬解并占用名额` | 正常路径 |
| `auto：名额满时溢出到软解并如实标记` | 溢出 ≠ 格式不支持 |
| `释放名额后新的通道能重新拿到硬解` | 名额回收不泄漏 |
| `hardware 档无视名额：允许超额且不降级` | 显式指令优先 |
| `hardware 档即使格式不在白名单也不降级` | 核心承诺 |
| `software 档不占名额` | 档位隔离 |
| `名额下限被钳到 1，设为 0 被忽略` | 参数退化 |
| `重复释放不会回绕（饱和减法）` | 防饿死 |

## 已知限制 / 下一步

- 本模块只做**决策**，不执行 open；"决定走硬解但 open 失败"之后的处理由解码
  后端接入那一步负责（`auto` 记日志并落软解，`hardware` 保持失败）。
- 默认上限 4 是保守值，真机多路联调后再调。
- **core 层到此封顶。** 下一步（0010）进入解码层：FFmpeg 解封装与软解后端
  `ffsw`——第一个真正碰 FFmpeg 的节点，也是 `decode-smoke` 工具的基础。
