## 这个功能点做了什么

core 层有了解码线程与呈现线程之间的交接通道：`FrameQueue(T, capacity)` 是一个
有界、无锁、单生产者单消费者的环形队列。生产者 `push()` 永不阻塞，队列满时
返回 `false`；消费者用 `pop()` / `peek()` / `peekNext()` 取帧。

## 为什么现在做

它是"解码"和"呈现"两条线程唯一该共享的东西。更关键的是它**必须有界**：
无界队列在弱网下会把"丢帧"变成"内存一直长、延迟一直涨"，而直播流唯一正确的
背压就是丢掉旧帧。后面的帧回收环（0003）、呈现选择器（0004）、调度器（0006）
都要骑在它上面，所以它必须先立住。

## 实现要点

### 队列不替调用方决定丢谁

`push()` 在满时返回 `false`，**不覆盖旧元素**。丢最旧还是丢最新取决于场景
（实时流丢最旧、关键帧优先场景可能丢别的），这是策略不是机制，队列不该替
调用方做主。调用方拿到 `false` 之后可以自己决定重试、丢弃、还是记账。

### 空与满靠留一个空槽区分

容量为 `capacity` 的数组只用 `capacity - 1` 个槽位，因此不需要引入
一个被两个线程同时写的计数器。"可用槽位 = 容量 - 1"是反直觉的约定，容易
在调用方那里算错，所以把它做成了公开常量 `usable_capacity`，让调用方和测试
都能引用同一个来源，而不是各自写 `- 1`。

### 内存序与伪共享

读自己的下标用 `.monotonic`（那个下标只有本线程写），跨线程读对方的下标用
`.acquire`，写自己的下标用 `.release`。两个下标各自 `align(cache_line)`，
把生产者和消费者的热点分开——否则两个线程会不停争同一条 cache line。

### 容量约束在编译期挡住

`capacity < 2` 或不是 2 的幂，直接 `@compileError`。环形队列用 `index & (cap-1)`
做回绕，非 2 的幂会静默算错下标，这种错误不该留到运行时。

## 单元测试覆盖了什么

| 测试 | 锁定的行为 |
|---|---|
| `可用槽位是容量减一` | 反直觉约定的单一来源 |
| `初始状态为空且未满` | 初始态与空队列 `pop` 语义 |
| `push 与 pop 往返同一个值` | 基本往返 |
| `保持先进先出顺序` | FIFO 顺序 |
| `承载真实载荷形状（带时间戳的帧）且字段不丢失` | 结构体载荷按值搬运，字段不被破坏 |
| `pop 空队列返回 null` | 可重复调用的空语义 |
| `peek 不消费，peekNext 在元素不足时返回 null` | 窥视的非破坏性；0/1/2 个元素三个边界 |
| `满时 push 失败且不会覆盖已有元素` | 失败的那次 `push` 不污染队列 |
| `pop 腾出空间后可以继续 push` | 满→未满的状态迁移 |
| `环形回绕多轮后顺序仍然正确` | 下标回绕（5 轮填满/排空） |
| `队列移交堆分配的所有权` | 载荷所有权随元素转移 |
| `SPSC 并发下不丢帧、不重帧、总量守恒` | 真双线程 5 万次；三个不变量：全部消费、数量守恒、序号算术和守恒 |

并发测试特意加了"序号算术和守恒"这一条：只比较数量的话，**"丢一个又重复一个"**
这种内容错位的失败模式会漏过。

## 已知限制 / 下一步

- **不提供 `len()`**：长度需要跨线程读取两个下标，会引入额外的一致性要求。
  需要长度的调用方（统计上报）应该自己记账，而不是读队列。
- **只支持单生产者单消费者**：多生产者需要另一套设计（带 CAS 的多生产者环），
  当前管线里每路流只有一个解码线程，用不上。
- 下一步（0003）：帧回收环。解码帧在交出去之后不能立刻释放（GPU 可能还在
  读它），回收环负责把"释放"推迟到呈现确认之后，并在队列满时立刻回收，
  避免弱网下帧的积压变成显存积压。
