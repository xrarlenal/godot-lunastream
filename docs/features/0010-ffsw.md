## 这个功能点做了什么

解码层有了第一个真正能出帧的后端：`ffsw`——FFmpeg 既解封装也软件解码，
每帧打包成 CPU 内存里的紧凑 NV12。它承担两件事：

1. **网络源的入口**。`rtsp://` / `http(s)://` / `udp://` / 本地路径都走同一个
   `avformat_open_input`，RTSP 一律 TCP 承载，读写超时可配（默认 5 秒）。
2. **格式兜底**。三个硬解后端覆盖的编码很窄（ffvt 只有 H.264，ffd3d/ffva 是
   H.264/HEVC），MPEG4 / VP9 / AV1 / MJPEG 原本没有任何通路。

顺带把 0010 第 1 步写错的一处契约修掉了，并给它加了守卫（见"实现要点"第 5 条）。

## 为什么现在做

core 层（0000–0009）封顶之后，第一个真正碰外部世界的模块就是它。选它先做是因为
**它能被机器验证**：不需要 GPU、不需要 Godot、不需要摄像头，喂一个文件就能跑完
整条"打开→解码→打包→归还"的路径，并和 ffmpeg 自己解的结果逐字节对照。

它也是 0012（`decode-smoke`）的基础：解码能不能跑，与"Godot 里能不能出画"是两件
事，前者可以进 CI，后者要等呈现层。

## 实现要点

### 1. 只重排布局，不做色域换算

`ffsw` 的输出是 NV12，**矩阵、码值范围、位深对齐一概不动**：它们是 core 色彩层
（0006）与共享 GLSL compute 的职责，硬解与软解必须喂同一份 shader，否则两条路
各有一套颜色。这条约束是可验证的：自检把整条流写成原始 NV12，与
`ffmpeg -pix_fmt nv12 -f rawvideo` 的输出**逐字节相同**——任何一个色值被动过，
这个比对立刻就红。

`swscale` 用 `SWS_BICUBIC`（也就是 ffmpeg 命令行不给 `-sws_flags` 时的默认值）。
这一条是被对照实验逼出来的：最初用 `SWS_BILINEAR`，4:2:0 源照样逐字节一致
（那种情况根本不发生色度重采样），但 4:4:4 源在第 19217 字节开始就不一样了——
色度下采样滤波不同。对齐到 ffmpeg 的默认之后，4:4:4 / 4:2:2 源也能逐字节比对。

### 2. 槽位环：12 槽、耗尽不丢帧

帧的存储由 shim 内部一个 12 槽的环持有，容量取自 core 的公式
`requiredPoolDepth(队列可用槽位=7, frame_latency=4) = 7 + 1 + 4`。稳定态下取帧
与归还都不碰堆（尺寸不变时缓冲整体复用）。

三处刻意的语义：

- **耗尽返回 NONE，而且不丢帧**：已经解出来的那一帧留在手上（`frame_pending`），
  下次调用先交付它。如果耗尽时直接丢掉，NONE 就变成了"静默丢帧"。
- **归还幂等**：重复归还、归还 NULL 都是空操作，不会把别人正在写的槽位抢回来。
  这样"某一路忘了归还"的后果是这条流停帧（可复现），而不是踩内存。
- **轮转分配**：从游标处找空槽，而不是固定复用 0 号槽，避免一块缓冲被反复改写
  把消费者手上那份踩掉。

### 3. 网络源必须能"收场"（三条都是实测逼出来的）

第一版没有超时。实测把 UDP 推流停掉之后，进程在 `av_read_frame` 里**永久挂住**
（我手工 `pkill` 才收掉）。实时源死掉是常态，不是异常，于是补上：

| 措施 | 解决的现象 |
|---|---|
| `rw_timeout` / `timeout` / `stimeout`（默认 5 秒，新增 `nv_ffsw_set_io_timeout_us`） | 源停掉后解码线程永久阻塞 |
| RTSP 一律 `rtsp_transport=tcp` | UDP 承载丢包会让帧碎片化；不少摄像机默认 UDP |
| 坏包（`AVERROR_INVALIDDATA`）跳过并计数 | 中途接入 UDP 时，**第一个坏包就把整条通道打死**（0 帧、直接 FAIL） |

同时把两种"结束"分开上报：读到流尾是干净的 `NONE`，源中途死掉是 `FAIL` 且
`last_error` 写明 `read failed (-5)`。它们的区别就是调用方接下来该做什么——
继续等，还是重开（0008 的重连状态机正是为后者存在的）。

### 4. 解码器只开单线程

`thread_count = 1`：多路并行已经由 core 的 worker 池承担（每路流一个 worker），
这里再开解码器内部线程等于与 worker 池抢核。`pkt_timebase` 按流的时间基设置，
否则 `best_effort_timestamp` 的换算就是错的（PTS 会整体偏）。源没给时间戳时按
帧率往前推，保持单调。

### 5. 修一处契约错位，并给它加守卫

第 1 步写的头文件声称"标签数值与 `backend.zig` / `color.zig` 一致"，但传输函数
那一组是错的：头文件写 `PQ = 2, HLG = 3`，而 core 里 `2/3` 是 `gamma22/gamma28`
（PQ 是 4、HLG 是 5）。后果很隐蔽——Zig 侧 `@enumFromInt` 不报错，PQ 片源被读成
gamma22，颜色默默错掉。

修法是两头一起：数值对齐，并新增 `src/ffsw/ffsw_shim_abi_test.zig`——把 C 头文件
当**文本**读进来（`@embedFile`），逐项比对数值，再按组数个数（防止"core 加了
成员、shim 忘了跟"这种只在新特性上才暴露的漏改）。它不需要 FFmpeg、不需要 GPU，
因此进了 `zig build test`。

## 这个功能点的"测试"是什么

`src/core/` 的单测表达不了这个 shim（它要真的碰 FFmpeg、真的解一个文件），
所以替代品是两道机器验证的关卡：

| 关卡 | 命令 | 覆盖 |
|---|---|---|
| C ABI 标签守卫 | `zig build test` | 6 项：四组标签逐项数值一致 + 数量一一对应 + 解析器不静默通过 |
| 端到端自检 | `zig build ffsw-selftest` | 30 项检查 + 与 ffmpeg 的逐字节比对 |

自检分两段：

- **[A] 内容与顺序**：probe 不开解码器也能拿到编码分类与尺寸；open 与 probe 的
  尺寸一致；首帧 stride == 宽度（紧凑无填充）、位深 8、两个平面都有指针；每一帧
  尺寸稳定；PTS 非递减（0005 呈现选择器的前提）；首帧亮度均值 > 1（确认真的解出
  了画面，而不是一屏黑）；流尾之后持续返回 `NONE`；有界源没有坏包；
  `close` 之后查询退化为 0 而句柄仍可用。
- **[B] 槽位环**：不归还地连取满 12 帧都成功 → 第 13 次返回 `NONE` 且
  `last_error` 仍为空（背压不算错误）→ 归还一帧后立刻续上，且 PTS 继续前进
  （证明耗尽那一轮没丢帧）→ 重复归还与归还 NULL 是空操作 → 归还之后能继续解到流尾。

## 验证方式与结果

```bash
zig build test            # 114/114 通过（108 core + 6 shim ABI 守卫）
zig build ffsw-selftest   # 7/7 步成功；30 项检查 0 失败；cmp 逐字节一致
```

具体观察：

| 场景 | 结果 |
|---|---|
| 有界源（mpeg4/mp4，320x240@25，2 秒） | 解出 50 帧；`cmp` 与 ffmpeg 输出**逐字节一致**（5 760 000 字节） |
| 4:4:4 源（H.264 High 4:4:4） | swscale 转 NV12 后同样逐字节一致（对齐 `SWS_BICUBIC` 之后） |
| 10-bit 源（H.264 High 10） | 按设计**显式失败**：`10-bit software decode not implemented yet (see 0011)`；`open_info` 已如实报 `depth=10` |
| UDP 实时源（H.264/mpegts，手工） | 解出 25 帧，25 项检查全过（PTS 4.400→5.360s） |
| RTSP 实时源（mediamtx + H.264，手工） | 解出 25 帧，25 项检查全过；**服务端日志确认承载是 TCP**：`is reading from path 'live', with TCP, 1 track (H264)` |
| 源中途死掉（推流 3 秒后停止） | 不再挂起：约 13 秒内以 `read failed (-5)` 收场（此前会永久阻塞） |

### 验证过程中顺带查清的一件事（与本次改动无关）

`zig build test` 的输出里会出现一行 `failed command: .../test --listen=-`，看着像
有测试挂了，但同一份输出里的摘要写着"5/5 steps succeeded; 114/114 tests passed"，
退出码也是 0。用隔离实验定位到：**只要某个测试往 stderr 写一行，zig 0.16 的
build runner 就会多打这一行**。做法是给 ABI 测试临时加一句 `std.debug.print`——
那一行之前没有、加了就有；去掉又消失。core 那一步本来就有（0007 的 PTS 回退告警
走 `std.log`，落 stderr），所以它一直带着这一行。属于 zig 的呈现行为，不是失败。

## 已知限制 / 下一步

- **10-bit 未做**：`yuv420p10le` / P010 走 0011。当前是"显式失败并指向 0011"，
  绝不是静默降到 8-bit（那会让 10-bit 片源悄悄丢掉低两位）。
- **还没接到引擎**：`ffsw` 只有 C ABI，Godot 侧拿不到它——接线属于 0018。因此
  这一段的能力目前只能通过 `zig build ffsw-selftest` 与手工烟测观察。
- **只在 macOS 上跑过**：Windows / Linux 未编译、未验证。
- **`NONE` 与"流结束"在 Zig 接口上是同一个值**——这是留给 0018 的坑：
  `core/backend.zig` 的 `next_video_frame` 返回 `?VideoFrame`，`null` 会被
  `pumpStream` 当成 `eos`（该流从此不再请求新帧）。所以"槽位耗尽返回 NONE"这条
  契约在接进引擎之前必须解决：要么让 vtable 能区分"暂时没有"与"到头了"，
  要么保证槽位永不耗尽。当前的 12 槽是按 core 的表面数量公式取的，正常释放
  的消费者撞不到上限；但这条约束必须在接线那一步落实成代码，而不是靠注释。
- **音频/字幕流被直接丢弃**（`av_packet_unref` 后继续），与"只做视频"的定位一致。
- 下一步（0011）：10-bit 软解路径，统一右对齐 16-bit 容器。
