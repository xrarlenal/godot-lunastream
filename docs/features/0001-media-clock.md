## 这个功能点做了什么

core 层现在有了时间基准：`MediaClock` 提供"当前播放到第几秒"，`WallClockMs`
提供带类型的单调挂钟毫秒。解码调度、呈现早晚判定、断流重连退避、状态上报
四件事从此有同一个时间来源。

## 为什么现在做

它是后面几乎所有东西的前提：帧队列要按时间戳判早晚、呈现选择器要算迟到多久、
重连要算退避间隔、"停滞"检测要算多久没有新帧。而且它是纯计算、零依赖，
可以在任何机器上验证——先把最容易锁死语义的一层做掉。

## 实现要点

### 三个语义被刻意分开

源工程把"改时间"这件事混在几个方法里，复刻时把它拆成三条互不重叠的语义，
每条都有测试锁定：

| 方法 | 语义 | 允许回拨 |
|---|---|---|
| `advance(delta)` | 按渲染 delta 推进 | 不适用（负 delta 直接忽略） |
| `seekTo(t)` | 显式绝对定位 | **是**——seek 的语义就是回拨 |
| `reanchor(t)` | 断流重连后向前对齐 | **否**——只向前，且返回是否生效 |

`reanchor` 的"只向前"是这一层最值钱的约束：重连后新帧的时间戳往往比本地时间
略旧，如果无条件赋值，画面会跳回旧帧。源工程在 `ClockBridge.reanchorToAudio`
的注释里提到了 "without a backward jump"，但没有把它做成一个可测试的返回值；
这里补上了返回值，让调用方能区分"锚定生效"与"锚定被忽略"两种现场。

### 与源工程的差异（已记录，不是遗漏）

源工程 `clock.zig` 有三个类型：`MonotonicClock`、`AudioMasterClock`、
`ClockBridge`（运行时切换主导方）。本模块**只复刻单调推进这一条路径**，
原因是：插件定位是"视频源"，网络流后端（ffvt / ffd3d / ffva / ffsw）本身
不解码音频，没有音频时钟可以做主。

若将来把带音频的本地文件路径（源工程的 avf / mf 后端）也迁进来，本模块需要
扩展出"可切换主导方"的形态。届时按同一流程**单独提一个功能点**，而不是现在
就把用不到的分支铺进来。

### 挂钟时间戳为什么要做成类型

`WallClockMs` 是裸 `f64` 的包装：构造显式、不提供到 `f64` 的隐式转换。
它防的是一类具体错误——把"媒体时间"和"挂钟时间"两个同为 `f64` 的量互相赋值。
两者单位都是秒/毫秒但基准完全不同，混用后表现为"退避间隔算错"或"停滞判定误报"，
而编译器不会提醒。

## 单元测试覆盖了什么

| 测试 | 锁定的行为 |
|---|---|
| `初始位置为零` | 默认从 0 开始且未暂停 |
| `初始位置可以被指定` | 构造时可指定起点 |
| `advance 按 delta 累加` | 多次推进可累加 |
| `暂停时 advance 不推进` | 暂停语义 |
| `解除暂停后继续累加` | 暂停期间不补时间 |
| `负 delta 与零 delta 都不推进（时间不倒流）` | 时间不倒退 |
| `seekTo 允许回拨` | seek 与推进语义分离 |
| `reanchor 只向前：回拨请求被忽略` | 重连不跳回旧帧 |
| `reanchor 向前时生效并报告已锚定` | 返回值语义 |
| `reanchor 与当前相同不算锚定` | 边界相等的情形 |
| `暂停状态下 reanchor 仍然生效` | 它改绝对位置而非推进 |
| `WallClockMs 承载原始值并支持求差` | 双向求差（含负值） |
| `WallClockMs 默认值为零` | 默认构造 |
| （0000 遗留）`core 模块可以编译并被引用` ×2 | 模块根可用 |

## 已知限制 / 下一步

- 本模块不提供真实时钟读数（不读系统时间），只是被动的累加器。**主动时钟**
  （读单调挂钟、按真实经过时间推进）与线程原语（`Mutex` / `Condition` /
  `sleep`）留到 0006 有界 worker 池那一步一起做——它在 Zig 0.16 里需要适配
  `std.Io` 的新形态，和线程放在一起改比单独改更容易验证。
- 下一步（0002）：有界帧队列。它依赖本模块提供的时间戳语义，并为 0006 的
  调度器与呈现管线提供交接点。
